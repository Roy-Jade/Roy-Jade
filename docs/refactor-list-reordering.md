# Réorganisation des listes

**Statut : phase 1 terminée, phase 2 close (YAGNI, pas d'implémentation), phase 3 terminée.**

Aucun pattern de drag-and-drop n'existait dans le code avant ce chantier (recherche confirmée : zéro occurrence de `drag`/`dnd-kit`/`react-beautiful-dnd`/`sortable`/`reorder` dans `frontend/`). **Décision actée : boutons haut/bas plutôt que drag-and-drop**, pour éviter une nouvelle dépendance et rester accessible au clavier sans effort supplémentaire.

Trois ordres distincts sont concernés, découpés en phases pour livrer vite le morceau sans migration :

## Phase 1 — Tâches d'une expérience/formation (fait)

Le schéma était déjà prêt : `experience_task`/`formation_task` ont une colonne `position`, et `insertTasks` (`backend/src/utils/editInJunctionTable.ts`) dérive déjà cette position de l'ordre du tableau `tasks: string[]` reçu (`tasks.flatMap((_, i) => [tasks[i], i+1])`). Aucun changement backend nécessaire.

**Implémentation :** ajout d'un helper `moveItem<T>(items, from, to)` (échange deux éléments d'un tableau, no-op si hors bornes) dans `ExperienceForm.tsx` et `FormationForm.tsx` — dupliqué dans les deux fichiers, sur le modèle de `toggleId` déjà dupliqué de la même façon. Deux boutons `↑`/`↓` (`aria-label`, désactivés en bout de liste) ajoutés à côté de chaque ligne de tâche, appelant `setTasks(p => moveItem(p, i, i±1))`.

**Vérification :** `tsc -p tsconfig.app.json` propre. Pas de test live via l'admin (pas d'accès au mot de passe admin dans cette session) — la logique s'appuie sur `insertTasks`, déjà couvert par la suite de tests backend existante, et le swap côté front est trivial. **À confirmer manuellement.**

## Phase 2 — Hardskills/softskills sélectionnés dans une expérience/formation (clos, YAGNI)

**Constat :** `experience_hardskill`, `experience_softskill`, `formation_hardskill` sont de pures tables de liaison (`id`, `<ref>_id`, `<second>_id`, `UNIQUE`), sans colonne d'ordre explicite.

**Découverte en investiguant l'implémentation :** le rendu actuel (`ExperienceItem.tsx`/`FormationItem.tsx`) affiche déjà les hardskills avant les softskills — deux `.map()` séparés dans un ordre fixe, aucun changement nécessaire sur ce point. À l'intérieur de chaque liste, l'ordre observé aujourd'hui (qui *semble* groupé par catégorie) vient en réalité d'un effet de bord non documenté de PostgreSQL : `JSON_AGG(DISTINCT jsonb_build_object(...))` trie ses objets par la longueur de leur clé la plus courte — comme chaque objet hardskill/softskill inclut une clé `id` (l'id de la ligne de liaison, `hardexp.id`/`softexp.id`), qui est la clé la plus courte, le tri résultant correspond déjà à l'ordre d'ajout (id de liaison croissant). Vérifié empiriquement via des requêtes synthétiques (`VALUES` non liées aux vraies données) faisant varier `id` et `category` en sens opposés — `id` gagne systématiquement. L'apparence de groupement par catégorie vient du picker `HardskillChecklist` (groupé par catégorie à la sélection), pas d'un tri SQL sur la catégorie.

**Décision (YAGNI) :** ne rien changer. Le fix propre (sous-requêtes corrélées avec `ORDER BY` explicite, remplaçant le `JOIN`+`GROUP BY`+`DISTINCT`) a été évalué et écarté — l'impact visuel d'un tri non garanti mais qui fonctionne est quasi nul, et toucher un pattern SQL partagé par 4 fichiers pour ce gain n'est pas justifié. Point à revoir seulement si ce comportement casse un jour de façon visible (ex. montée de version Postgres, refactor du builder jsonb).

## Phase 3 — Listes de l'aside : hardskill, softskill, langue, loisir (fait)

**Constat de départ, corrigeant une mémoire obsolète :** `hardskill`, `softskill`, `language`, `hobby` ne sont **pas** triées par `id` en pratique. Le correctif antérieur ([[project_ordering_bug]]) qui ajoutait `ORDER BY id` a été appliqué à `dashboardService.fetchDashboard`/`GET /dashboard` (`getOverview`) — un endpoint qui s'est avéré **du code mort**, appelé par aucun composant frontend (ni l'admin ni le CV public). Le vrai chemin de données (`GET /aside` → `languageService`/`hobbyService`, `GET /hardskill` → `hardskillService`, `GET /softskill` → `softskillService`) n'avait **aucun `ORDER BY`** : l'ordre dépendait de l'ordre physique de stockage Postgres, non garanti. Ce chantier corrige donc, au passage, un bug d'ordre resté actif sur le vrai chemin malgré un correctif antérieur cru suffisant.

**Schéma :** colonne `position SMALLINT NOT NULL` ajoutée sur les 4 tables (`migration.sql`, même convention que `experience_task.position` — pas de défaut, toujours fournie explicitement). Appliquée sur la base de dev déjà initialisée via `ALTER TABLE` + backfill (`position = ROW_NUMBER() OVER (ORDER BY id) - 1`, pour ne rien changer visuellement) + `SET NOT NULL`, exécuté manuellement (pas de framework de migrations incrémentales sur ce projet — `migration.sql` n'est rejoué qu'au premier init d'un volume Postgres vide).

**Backend :** `position` ajouté aux schémas Zod (`skill.ts` ×2, `language.ts`, `hobby.ts`) — automatiquement inclus dans les `KeyList` respectives (seul `id` est omis), donc patchable via les endpoints PATCH existants sans endpoint dédié. Les 4 `fetch*` (`hardskillService`, `softskillService`, `languageService`, `hobbyService`) gagnent `ORDER BY position`. Les 4 `add*` calculent la position côté serveur à l'insertion (`(SELECT COALESCE(MAX(position), -1) + 1 FROM <table>)`, append en fin de liste) — jamais acceptée depuis le payload de création, seulement en édition. Les 4 `getXById` (utilisés par `add`/`edit` pour renvoyer la ligne à jour) projettent aussi `position`.

**Frontend :** boutons `↑`/`↓` (`aria-label`, désactivés en bout de liste) ajoutés dans les 4 composants `Dashboard*.tsx` (`DashboardHardskill`, `DashboardSoftskill`, `DashboardLanguage`, `DashboardHobby`), qui reçoivent un nouveau callback `onReorder(id, direction)`. Implémenté dans `DashboardMenu.tsx` via un helper générique `swapPosition<T extends {id,position}>(items, id, direction, patchFn)` : trouve l'item et son voisin dans le tableau déjà trié reçu du fetch, échange leurs `position` via deux appels `patch*` successifs (décision actée : pas d'endpoint transactionnel dédié, impact d'un swap partiellement échoué purement cosmétique), puis invalide la query concernée (`['aside']` pour langue/loisir, `['softskill']`, `['hardskill']`).

**Point accepté sans changement :** `DashboardHardskill` réutilise `useHardskillData(filters.hardskillLevel, filters.hardskillCategories)`, la même liste **filtrée par le contexte CV courant** que le reste du menu cascade (contrairement à softskill/langue/loisir qui affichent toujours la liste complète). Par défaut (aucun filtre restrictif actif) la liste est complète ; si l'admin restreint le filtre CV pendant une réorganisation, l'ordre vis-à-vis des hardskills momentanément masqués peut devenir incohérent — cas marginal, purement cosmétique, laissé tel quel (même logique de scope que le reste du menu cascade, pas une régression introduite par ce chantier).

**Vérification :** suite de tests backend (`hardskillService.test.ts` mis à jour pour la nouvelle requête SQL exacte) — 234/237 (3 échecs pré-existants sans rapport). `tsc` backend et frontend (`-p tsconfig.app.json`) propres, `eslint` propre. Testé de bout en bout via `docker compose exec backend npx tsx` (appel direct de `editLanguage` en contournant l'auth, faute de mot de passe admin) : swap de position confirmé propagé jusqu'à `GET /api/cv/aside`, ordre restauré après test. **Pas de test via l'interface admin réelle (boutons ↑/↓ cliqués) — à confirmer manuellement.**

**Correctif de mise en forme (retour utilisateur après test réel) :** `.items-list__row-data` (`Dashboard.scss`) est une grille CSS avec un nombre de colonnes fixé par `--list-cols` (une colonne par info affichée + une dernière colonne de 20px prévue pour l'unique bouton d'édition d'origine). Les deux boutons ↑/↓ ajoutés en enfants directs supplémentaires débordaient donc sur une ligne implicite suivante (la grille ne compte que N colonnes, pas N+2). Corrigé en regroupant les 3 boutons (↑/↓/éditer) dans un conteneur `<span className="items-list__actions">` (une seule colonne, comme avant), avec `--list-cols` élargi de `20px` à `68px` sur cette dernière colonne (les 4 fichiers `Dashboard{Hardskill,Softskill,Language,Hobby}.scss`) et une classe partagée `.reorder-button` (boutons compacts 20×20px, cohérents avec `.edit-button`) dans `Dashboard.scss`. Point d'attention réglé au passage : la règle d'ellipse (`overflow:hidden` etc.) ciblait tout `span` descendant de `.items-list__row-data`, ce qui aurait aussi touché le nouveau conteneur `.items-list__actions` (aussi un `<span>`) — exclu explicitement via `span:not(.items-list__actions)`.
